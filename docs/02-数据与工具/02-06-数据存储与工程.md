# 数据存储与工程

## 一、为什么值得花时间在数据工程上

量化研究中，数据工程不是"准备工作"，而是研究本身的一部分。三个现实原因：

1. **你必然会重跑**。任何结论都需要在新数据上验证，如果每次重跑都要重新下载、重新清洗，你会倾向于减少重跑次数——而这正是过拟合的温床。
2. **数据会变**。财报重述、复权因子调整、成分股变更都会改变历史数据。没有版本管理，你无法判断"结果变了"是好事还是坏事。
3. **错误会累积**。一个未处理的缺失值进入因子，再进入回测，最后变成一条漂亮的曲线，你会花几天去找别的原因。

## 二、格式选型

| 格式 | 类型 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| CSV | 文本行式 | 人类可读、通用 | 无类型信息（日期/整数易错）、读写慢、体积大 | 小数据、人工核对、交换 |
| Parquet | 二进制列式 | 压缩率高（3~10×）、保留 schema、支持按列/谓词下推读取 | 不可直接阅读、需依赖库 | **默认选择** |
| Feather/Arrow | 内存映射格式 | 读写极快 | 不适合长期归档 | 中间结果、进程间传递 |
| SQLite/DuckDB | 嵌入式数据库 | 支持 SQL 查询、事务、并发 | 列存分析性能弱于 parquet | 元数据、研究日志、小表 |
| HDF5 | 科学数据格式 | 支持组内层次结构 | 并发写差、生态老旧 | 遗留项目 |

**实践建议**：行情数据用 parquet（按字段分文件或按年分区），元信息（数据版本、拉取时间、字段说明）与研究日志用 sqlite，中间缓存用 feather。

## 三、分区策略

分区的核心目的是**只读取需要的数据**，把 I/O 从"全量扫描"降到"少量文件"。

- **日频数据**：按年或按年月分区。常见布局：

```
storage/
  market/
    daily/
      year=2018/part-0.parquet
      year=2019/part-0.parquet
    adj_factor/
      year=2018/part-0.parquet
```

  宽表（dates × symbols）按年切分可以直接用日期范围定位。

- **分钟/tick 数据**：先按 symbol 分区，再按日期分区：

```
storage/market/minute/symbol=600519/date=2024-01-02.parquet
```

  因为高频查询几乎总是"某只股票某段时间"，按 symbol 优先更符合访问模式。

- **基本面数据**：按报告期分区，同时**额外保存披露日字段**，因为查询条件通常是披露日。

分区粒度不要过细：每年一个文件对日频数据合适；每天一个文件对全市场分钟数据会产生数十万个小文件，反而变慢。

## 四、缓存与增量更新

```python
import hashlib
import pandas as pd
from pathlib import Path

ROOT = Path("storage/market/daily")

def _version(df: pd.DataFrame) -> str:
    """用内容哈希做数据版本，保证任何改动都可被发现"""
    payload = pd.util.hash_pandas_object(df, index=True).values.tobytes()
    return hashlib.sha256(payload).hexdigest()[:12]

def save_partition(df: pd.DataFrame, year: int) -> str:
    path = ROOT / f"year={year}"
    path.mkdir(parents=True, exist_ok=True)
    file = path / "part-0.parquet"
    df.to_parquet(file)
    ver = _version(df)
    (path / "VERSION").write_text(ver)
    return ver

def load_partition(year: int) -> pd.DataFrame:
    return pd.read_parquet(ROOT / f"year={year}" / "part-0.parquet")

def incremental_update(new_df: pd.DataFrame) -> dict:
    """增量更新：只重写受影响年份的分区"""
    report = {}
    for year, part in new_df.groupby(new_df.index.year):
        old = load_partition(year) if (ROOT / f"year={year}").exists() else None
        merged = part if old is None else pd.concat([old, part])
        merged = merged[~merged.index.duplicated(keep="last")].sort_index()
        report[year] = save_partition(merged, year)
    return report
```

```python
import hashlib
import tempfile
from pathlib import Path

import pandas as pd

from qd.data.synthetic import generate_demo_market
from qd.utils.calendar import trading_days

# 用临时目录做演示，避免污染工作目录
ROOT = Path(tempfile.mkdtemp()) / "market" / "daily"

def _version(df: pd.DataFrame) -> str:
    payload = pd.util.hash_pandas_object(df, index=True).values.tobytes()
    return hashlib.sha256(payload).hexdigest()[:12]

def save_partition(df: pd.DataFrame, year: int) -> str:
    path = ROOT / f"year={year}"
    path.mkdir(parents=True, exist_ok=True)
    df.to_parquet(path / "part-0.parquet")
    ver = _version(df)
    (path / "VERSION").write_text(ver)
    return ver

def load_partition(year: int) -> pd.DataFrame:
    return pd.read_parquet(ROOT / f"year={year}" / "part-0.parquet")

def incremental_update(new_df: pd.DataFrame) -> dict:
    """增量更新：只重写受影响年份的分区"""
    report = {}
    for year, part in new_df.groupby(new_df.index.year):
        old = load_partition(year) if (ROOT / f"year={year}").exists() else None
        merged = part if old is None else pd.concat([old, part])
        merged = merged[~merged.index.duplicated(keep="last")].sort_index()
        report[year] = save_partition(merged, year)
    return report

md = generate_demo_market(n_symbols=50, start="2018-01-01", end="2024-12-31", seed=7)
close = md.close()

print("写入版本:", incremental_update(close))      # 写入并记录版本
print("读取 2020 年分区:", load_partition(2020).shape)
print("2024 交易日数:", len(trading_days("2024-01-01", "2024-12-31", market="A")))
print("2024 交易日数:", len(trading_days("2024-01-01", "2024-12-31", market="A")))
```

要点：

- **幂等性**：同一个输入数据重复写入应得到同一个版本号。这让"结果是否变化"变成可判定的问题。
- **去重规则要明确**：`keep="last"` 表示新数据覆盖旧数据，这对财报重述是正确的（用最新值），但对 point-in-time 研究是错的（需要保留所有快照）。
- **增量而非全量**：网络源限流严重时，每天只拉增量可以把拉取时间从小时级降到秒级。

## 五、可复现的数据版本管理

可复现需要三件事同时被记录，缺一不可：

| 要素 | 记录方式 | 用途 |
| --- | --- | --- |
| 数据版本 | 内容哈希 / 快照日期 / 拉取时间 | 判断结果变化是否来自数据 |
| 代码版本 | git commit hash | 判断结果变化是否来自逻辑 |
| 参数与环境 | 参数文件 / 依赖锁文件 | 保证别人能重跑 |

推荐的最小实现：每次回测把这三个值写进结果文件（如 `results/<exp_id>.json`），并且**结果文件名里带数据版本号**。这样半年后你看到一个 `ic_report_v3a9f2c1.json`，就知道它对应哪份数据。

## 六、一个可复现性的判据

可复现可以用一句话检验：**给定数据版本 $D$、代码版本 $C$、参数 $\theta$，重跑得到的净值序列 $V$ 必须唯一**。形式化地：

$$V = \mathrm{Backtest}(D, C, \theta)$$

三者中任何一个变化都应产生不同的结果标识。因此产出文件的命名应携带全部三个标识，例如 `res_v3a9f2c1_a1b2c3d_p007.json`。若只记录其中两个，你就无法定位变化来源。

## 七、工程清单

1. 原始数据只读，永不被覆盖；所有清洗产出到独立目录。
2. 清洗脚本是幂等的：同样的输入跑两次得到同样的输出。
3. 每个数据集附带 `SCHEMA.md`（字段、单位、口径、来源、拉取日期）。
4. 有元数据表记录每次拉取的行数、缺失率、异常值数量，异常波动要告警。
5. 定期做完整性检查：交易日数量是否匹配 `trading_days`、缺失率是否突变。

## 常见坑

- **用 CSV 存日频全市场数据**。几 GB 的 CSV 每次读取要几十秒，且日期被读成字符串后与 pandas 时间戳比较会静默失败。
- **过度分区**。数十万个小文件会让文件系统与读取都变慢，也会耗尽 inode。
- **缓存永不失效**。缓存了错误数据却不清理，是最难排查的一类 bug。缓存必须带版本，且提供显式失效方式。
- **用 `keep="last"` 合并 point-in-time 数据**，把财报快照覆盖掉，研究结论无法复现。
- **把中间结果当数据源**。某个因子面板被反复修改却不记录来源，半年后没人知道它怎么来的。
