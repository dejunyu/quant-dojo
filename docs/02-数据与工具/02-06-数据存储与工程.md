# 数据存储与工程

## 学完这一篇，你能做到

- 说清为什么"数据存得好不好"会直接决定一个研究结论可不可信
- 在 CSV / Parquet / SQLite 之间做出合理选型，不靠感觉
- 理解分区、缓存、增量更新各自解决什么问题
- 建立"数据版本 + 代码版本 + 参数"三件套，实现任意历史结果可复现

## 本篇要点

- 列式存储（Parquet）是行情数据的默认选择：压缩高、带类型、能按列读
- 分区的目的是**只读需要的那部分**，不是把文件切得越碎越好
- 可复现三要素缺一不可：数据版本、代码版本、参数与环境
- **原始数据只读、永不覆盖**——这是所有工程规矩里的第一条

## 一、从一篇改变了多国政策的论文说起

2010 年，哈佛经济学家**卡门·莱因哈特**（Carmen Reinhart）和**肯尼斯·罗格夫**（Kenneth Rogoff）发表了一篇论文《债务时代的增长》（*Growth in a Time of Debt*）。

结论很醒目：**当一国公共债务超过 GDP 的 90%，经济增长会大幅下滑**（论文里写的是平均 -0.1%）。2008 年金融危机之后，这个数字被欧美政客反复引用，成了推行财政紧缩政策的核心依据——美国"保罗·瑞恩预算案"里，关于高债务后果的**唯一**引用证据就是它。

问题是：**论文没有公开数据**。

2013 年，马萨诸塞大学阿默斯特分校的 **Thomas Herndon、Michael Ash、Robert Pollin** 三人（常缩写为 HAP）向作者索取到了那份 Excel 原始表格，逐格检查后发现了三类问题：**编码错误、选择性排除可用数据、非常规的加权方式**。最著名的一处是 Excel 公式漏选了若干国家。

修正之后，那个"债务超 90% 就增长崩塌"的结论变成了：**平均实际 GDP 增长 +2.2%，而不是 -0.1%**——和债务较低时**没有显著差别**。（[Wikipedia: Growth in a Time of Debt](https://en.wikipedia.org/wiki/Growth_in_a_Time_of_Debt)）

> **请注意整件事最刺眼的不是那个 Excel 错误，而是"数据没有公开"。**
> 论文 2010 年发表，影响多国政策三年，直到 2013 年一个 28 岁的博士生把原始表格要来复算，才发现问题。
> **如果数据从一开始就是可复现的，这个错误活不过一周。**

这个故事有三层，正好对应本篇的三件事：

| 故事的教训 | 对应工程动作 |
| --- | --- |
| 别人拿不到原始数据 → 无法验证 | **数据要带版本、可交付、可重跑** |
| 一个公式漏选几行 → 结论反转 | **清洗脚本要幂等、可审计、留痕** |
| 结果影响了三年政策 | **产出文件必须能追溯到"哪份数据 + 哪版代码"** |

> 德鲁克那句"你无法管理你无法衡量的东西"，在这里可以换个说法：
> **你无法复现你没有记录的东西。**
> 而一个不能复现的结论，**和没有结论只差一个漂亮的表格**。

## 二、为什么数据工程不是"准备工作"

很多人觉得存数据是脏活，先随便存着，等研究做出成果再整理。这是错的，有三个现实原因：

1. **你必然会重跑。** 任何结论都要在新数据上验证。如果每次重跑都得重新下载、重新清洗，你会下意识**减少重跑次数**——而这正是 01-03 讲的过拟合温床。
2. **数据会变。** 财报重述、复权因子调整、指数成分变更，都会改写历史。没有版本管理，你分不清"结果变了"是发现了新东西，还是数据被悄悄改了。
3. **错误会累积。** 一个没处理的缺失值进入因子、再进入回测，最后变成一条漂亮曲线——你会花几天去查别的原因，根本想不到是三个月前那次 `fillna`。

> 一句话：**数据工程不是研究的前奏，是研究的一部分。**
> 你把数据管得多清楚，决定了你半年后还敢不敢相信自己写下的结论。

## 三、格式选型（逐个说清为什么）

| 格式 | 类型 | 优点 | 缺点 | 什么时候用 |
| --- | --- | --- | --- | --- |
| **CSV** | 文本、行式 | 人能直接读、通用 | **无类型信息**（日期/整数容易读错）、读写慢、体积大 | 小数据、人工核对、对外交换 |
| **Parquet** | 二进制、**列式** | 压缩 3~10 倍、保留 schema、支持按列读取 | 不能直接眼看、需依赖库 | **行情数据默认选择** |
| **Feather / Arrow** | 内存映射 | 读写极快 | 不适合长期归档 | 中间结果、进程间传递 |
| **SQLite / DuckDB** | 嵌入式数据库 | 支持 SQL、事务、并发 | 列存分析不如 parquet | 元数据、研究日志、小表 |
| **HDF5** | 科学数据格式 | 支持层次结构 | 并发写差、生态偏老 | 遗留项目 |

> **为什么 Parquet 是默认？** 关键在于"**列式**"两个字。
> 一张行情表有 50 列，但你算动量因子只需要 `close` 一列。
> CSV 得把整行全读进来再挑；Parquet 可以**只把 close 那一列从磁盘取出来**。
> 数据量大到几十 GB 时，这不是"快一点"，是"能不能跑得动"的区别。
>
> 补个常识：**schema** 就是"每一列叫什么、是什么类型"。CSV 里 `2024-01-02` 到底是字符串还是日期，全靠读的人猜——**这类静默错误最坑**，因为不报错，只是算出来不对。

**实践建议**：行情用 Parquet（按字段分文件或按年分区）；数据版本、拉取时间、字段说明和研究日志用 SQLite；中间缓存用 Feather。

## 四、分区：不是切得越碎越好

分区的唯一目的：**只读需要的那部分数据**，把 I/O 从"全量扫描"降到"打开几个文件"。

| 数据频率 | 分区键 | 为什么 |
| --- | --- | --- |
| 日频 | 年 / 年月 | 查询几乎总是"某段时间"，按日期定位最快 |
| 分钟 / tick | 先 symbol、再日期 | 高频查询几乎总是"某只股票某段时间" |
| 基本面 | 报告期，**另存披露日字段** | 查询条件常是披露日（见 02-04） |

典型布局：

```
storage/market/daily/year=2018/part-0.parquet
storage/market/minute/symbol=600519/date=2024-01-02.parquet
```

> ⚠️ **别过度分区。** 日频每年一个文件很合适；但全市场分钟数据如果每天一个文件，会产生**数十万个小文件**，文件系统和读取都变慢，甚至耗尽 inode。
> **分区粒度要匹配"你平时怎么查它"**，不是越细越专业。

## 五、缓存与增量更新（代码逐个讲透）

下面这段是本篇的核心示例。它做三件事：**给每份数据算一个内容指纹（版本）、只重写受影响的年份、保证重复写入结果一致**。

```python
import hashlib
import tempfile
from pathlib import Path

import pandas as pd

from qd.data.synthetic import generate_demo_market
from qd.utils.calendar import trading_days

# 用临时目录做演示，避免污染工作目录
ROOT = Path(tempfile.mkdtemp()) / "market" / "daily"

def _version(df: pd.DataFrame) -> str:
    """用内容哈希做数据版本：任何改动都会被发现"""
    payload = pd.util.hash_pandas_object(df, index=True).values.tobytes()
    return hashlib.sha256(payload).hexdigest()[:12]

def save_partition(df: pd.DataFrame, year: int) -> str:
    path = ROOT / f"year={year}"
    path.mkdir(parents=True, exist_ok=True)
    df.to_parquet(path / "part-0.parquet")
    ver = _version(df)
    (path / "VERSION").write_text(ver)
    return ver

def load_partition(year: int) -> pd.DataFrame:
    return pd.read_parquet(ROOT / f"year={year}" / "part-0.parquet")

def incremental_update(new_df: pd.DataFrame) -> dict:
    """增量更新：只重写受影响年份的分区"""
    report = {}
    for year, part in new_df.groupby(new_df.index.year):
        old = load_partition(year) if (ROOT / f"year={year}").exists() else None
        merged = part if old is None else pd.concat([old, part])
        merged = merged[~merged.index.duplicated(keep="last")].sort_index()
        report[year] = save_partition(merged, year)
    return report

md = generate_demo_market(n_symbols=50, start="2018-01-01", end="2024-12-31", seed=7)
close = md.close()

print("写入版本:", incremental_update(close))
print("读取 2020 年分区:", load_partition(2020).shape)
print("2024 交易日数:", len(trading_days("2024-01-01", "2024-12-31", market="A")))
```

我实跑的结果（版本号是内容哈希，每次运行一致）：

```
写入版本: {2018: '617cb2002a4a', 2019: 'dc68f1b4bd1c', 2020: '6450f0df1dc0', ...}
读取 2020 年分区: (262, 50)
2024 交易日数: 262
```

三个要点，逐个说：

- **`_version` 在干什么**：把整张表的内容做一次哈希（SHA-256），取前 12 位当"指纹"。**只要有一个数字变了，指纹就变**。这就是"数据版本"最朴素也最可靠的实现——不靠人写 `v2_final_final.csv`。
- **幂等性**：同一份输入重复写入，得到**同一个版本号**。这让"结果是否变化"变成一个可判定的问题，而不是凭感觉。
- **`keep="last"` 是个陷阱**：上面这句表示"新数据覆盖旧数据"。对**财报重述**是对的（用最新值），但对 **point-in-time 研究是错的**——你需要保留**所有历史快照**，不能覆盖（回想 02-04 和 Reinhart-Rogoff：错误往往就藏在"覆盖"里）。

> 补个常识：**哈希（hash）** 可以理解为"给任意大小的数据算一个固定长度的指纹"。
> 它的性质正好是工程需要的：**内容相同 → 指纹必相同；内容差一点 → 指纹完全不同**。
> 所以 `ic_report_v3a9f2c1.json` 这种文件名，一看就知道对应哪份数据。

## 六、可复现：三件套，缺一不可

一个结果能被复现，需要同时记录三样东西：

| 要素 | 怎么记 | 用来判断 |
| --- | --- | --- |
| **数据版本** | 内容哈希 / 快照日期 / 拉取时间 | 结果变化是不是来自数据 |
| **代码版本** | git commit hash | 结果变化是不是来自逻辑 |
| **参数与环境** | 参数文件 / 依赖锁文件 | 别人能不能原样重跑 |

写成一句判据（本篇唯一公式，逐个符号都好懂）：

$$V = \mathrm{Backtest}(D,\ C,\ \theta)$$

| 符号 | 意思 | 白话 |
| --- | --- | --- |
| $D$ | Data，数据版本 | 用的哪份行情 |
| $C$ | Code，代码版本 | 用的哪版程序 |
| $\theta$ | theta，参数 | 均线 20 日还是 60 日、成本几个 bp |
| $V$ | 净值序列 | 跑出来的结果 |

**整句话：给定同一份数据、同一版代码、同一组参数，重跑出来的净值必须唯一。**

所以产出文件命名应携带全部三个标识，例如 `res_v3a9f2c1_a1b2c3d_p007.json`。**只记两个，你就永远定位不到变化来源**——这正是 Reinhart-Rogoff 那三年里发生的事：结论变了，没人能说清是数据变了还是算法变了。

> 最小可行做法：每次回测把这三个值写进结果文件，并**让文件名带数据版本号**。
> 不需要上什么平台，一个 JSON 就够。**关键是每次都写，当场写。**

## 七、工程清单（照着做就行）

1. **原始数据只读，永不覆盖**；所有清洗产出到独立目录。
2. **清洗脚本幂等**：同样输入跑两次，得到同样输出。
3. 每个数据集附带 `SCHEMA.md`：字段、单位、口径、来源、拉取日期。
4. 元数据表记录每次拉取的**行数、缺失率、异常值数量**，异常波动要告警。
5. 定期做完整性检查：交易日数量是否匹配 `trading_days`、缺失率是否突变。

> 第 1 条最重要，也最常被破坏。它和 01-03 的研究日志是同一个精神：
> **别覆盖历史，别删失败记录。** 覆蓋掉的不是数据，是"当时到底发生了什么"的唯一证据。

## 八、把这一篇串起来

回到 2013 年那个 Excel 表格。

三位学者能推翻一篇影响多国政策的论文，靠的不是更聪明的模型，只是**把原始表格要来、逐格重算了一遍**。而这个动作之所以拖了三年，仅仅因为**数据没有被好好地公开和版本化**。

> 这跟 01-03 西蒙斯"停机重构"、02-04 时间旅行测试，是同一条线的三个站点：
> **能重来、能追溯、能证明，比"这次跑对了"重要得多。**

> 一句话收尾：
> **一次跑对不算研究，随时能重新跑对才算。**
> 而"随时"这两个字，全靠今天这些看起来一点都不酷的工程规矩撑着。

## 动手练习

- 把一份行情转存为按年分区的 Parquet，测量读取耗时与磁盘占用，和 CSV 对比。**先猜差多少倍，再跑。**
- 跑一遍上面的代码，然后**故意改动 close 里的一个数字**再写一次，看版本号怎么变。这就是"任何改动都可被发现"的直观体验。
- 给你最近一次回测的结果文件改名，带上数据版本与 git commit 短哈希。三个月后回来看，你会感谢自己。
