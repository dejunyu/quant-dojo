# 实盘延迟与系统

## 学完这一篇，你能做到

- 说清"延迟"到底由哪些环节组成，以及哪一环最危险
- 理解为什么**订单幂等比低延迟更重要**
- 知道风控为什么必须放在策略进程之外
- 用平台跑三档成本假设，并做一次断线故障模拟

## 本篇要点

- 延迟不是问题，**"你以为的价格"和"成交价"不一致**才是问题
- 最危险的不是慢，是**"以为没成交、又发一次"**（重复下单）
- 风控必须**独立于策略进程**：策略可以有 bug，风控不能跟着崩
- 断线后第一件事不是继续交易，是**对账**（reconciliation）

---

## 一、从"交易所自己出故障"说起

2013 年 8 月 22 日，纳斯达克经历了一次尴尬的事故：**它自己的撮合系统停了约 3 小时**。

**停牌从 12:14 开始，约 15:30 恢复——约 3 小时 11 分**，影响 3,200 多只纳斯达克上市股票。

起因不是单一 bug，而是一条**三段式的因果链**（据 NYT DealBook 对纳斯达克当时的复盘报道）：

1. NYSE 的 Arca 交易系统与纳斯达克的报价系统（SIP）之间**反复重连 20 多次**，并送来大量 **zero-dollar quotes**（防止陈旧报价的占位数据）；
2. 数据量超出 SIP 的设计容量，而 **SIP 没有"限流"（throttle）机制**；
3. SIP 切换到备用服务器，**备用系统的软件缺陷暴露**，于是全市场停牌。

纳斯达克当时的 CEO Robert Greifeld 说了一句很坦白的话：

> **"我们本该能够切换到备用系统，但我们没有做到。"**（"We were supposed to be able to fail over, and we did not."）

（[NYT DealBook 2013-08-29](https://archive.nytimes.com/dealbook.nytimes.com/2013/08/29/nasdaq-blames-a-surge-of-data-for-trading-halt/)）

> ⚠️ **别把这个事故简化成"纳斯达克自己写了个 bug"。**
> 真正的教训在第三段：**切换失败**。
> 备用系统写出来，不等于它在真出事时能用——**而"切换"这件事，平时几乎不可能被测到。**

> **这个故事对量化最直接的提醒是：连交易所都不是"永远在线"的。**
> 你精心设计的策略、校准好的延迟参数，
> **在一个"整个市场停摆 3 小时"的日子里，全都无效。**
>
> 而更现实的问题在你自己这一侧：
> **断线一次、重连慢一点、磁盘写满一次**——这些都不是"策略问题"，
> 但每一个都能让你错失一整天。

> 这也正好接上 06-07 的 Knight Capital：
> **Knight 死于部署失误，纳斯达克死于软件缺陷——两者的共同点是，问题都不在模型里。**

## 二、延迟链路：时间都花在哪

一次交易的时间线：

$$\underbrace{t_0}_{\text{市场成交}} \to \underbrace{t_1}_{\text{行情到你}} \to \underbrace{t_2}_{\text{计算信号}} \to \underbrace{t_3}_{\text{订单到交易所}} \to \underbrace{t_4}_{\text{撮合回报}}$$

| 环节 | 典型延迟 | 说明 |
| --- | --- | --- |
| **行情推送** | 毫秒~秒（Level-1 快照常 3 秒一次） | 你看到的"最新价"可能已过时 |
| 网络传输 | 1~50 ms | 跨省、跨运营商、Wi-Fi 都会放大 |
| 策略计算 | 微秒~秒 | 取决于模型复杂度与是否向量化 |
| 风控检查 | 1~10 ms | **前置风控是必需的** |
| 下单到交易所 | 1~50 ms | 柜台系统排队 |
| **撮合与回报** | 1~10 ms | **回报回程还有一次延迟** |

> **对日频策略，这些延迟合计 < 1 秒，几乎无影响。**
> 对分钟级开始有影响，**对秒级及以下，延迟就是全部**——
> 那时你要投入托管（colocation）、直连（DMA）、FPGA。
>
> **所以"要不要优化延迟"，取决于你的策略在什么时间尺度上赚钱。**

补两个常识：

- **Level-1 快照**：很多券商行情是"每 3 秒一张快照"，不是逐笔。
  **用快照做高频策略是灾难**——你看到的盘口是采样的，深度也不真实。
- **colocation（托管）**：把服务器放进交易所机房，把延迟从毫秒级降到微秒级。贵，而且只对高频有意义。

**关键认知**：延迟本身不是问题，**"你以为的价格"与"成交时的价格"不一致**才是。这个差值就是 [时机成本](./09-05-交易成本归因.md) 的物理来源。

## 三、两种"数据问题"：延迟与缺失

| 形态 | 是什么 | 回测里怎么处理 |
| --- | --- | --- |
| **延迟（latency）** | 数据是过去的 | "信号在 t 产生、交易在 t+k 执行" |
| **缺失（gap）** | 数据根本没到 | **几乎不建模，实盘必须处理** |

> **第二种才是杀手。** 延迟只是"数字旧了一点"，缺失是"你根本不知道发生了什么"。
> 断线、丢包、交易所停牌——**这些都是回测从不模拟、而实盘必然遇到的事。**

## 四、工程要求：四条命门

### 1. 幂等下单（最重要）

网络超时是最常见的故障：**你不知道订单是"没发出"还是"发了但回报丢了"**。

**解法**：客户端订单号（`clOrdId`）**幂等**——

- 每次下单生成唯一 ID，重试时**复用同一个 ID**；
- 交易所/柜台按 ID 去重，保证不会重复成交。

> **这是防止"重试导致双倍仓位"的唯一可靠手段。**
> 06-07 讲 Knight 那 45 分钟，核心机制之一就是**订单状态判断永远失败、于是无限发单**。
> **一个幂等 ID，能挡掉一整类灾难。**

### 2. 风控前置（且独立）

**风控必须在策略进程之外、在订单发出之前执行，且独立于策略代码。**

| 层级 | 检查项 | 失败动作 |
| --- | --- | --- |
| 语法层 | 价格/数量合规、涨跌停内、最小变动价位 | 拒绝 |
| 账户层 | 可用资金、可用持仓、可用融资额度 | 拒绝或缩减 |
| 组合层 | 单票集中度、行业集中度、总杠杆 | 拒绝或缩减 |
| 流速层 | 每秒订单数、撤单数、当日成交额 | **熔断暂停** |
| 净值层 | 回撤熔断（[08-05](../08-组合与风险/08-05-止损与回撤控制.md)） | 平仓并告警 |

> **一句话：策略代码可以有 bug，风控必须独立于它。**
> 如果风控写在策略进程里，**策略崩了，风控跟着崩**——那等于没有风控。

### 3. 断线重连与状态恢复

- **心跳与看门狗**：策略进程定期写心跳，监控发现超时就告警/重启；
- **重连后先对账**：用查询接口拉**真实持仓与未成交订单**，重建本地状态，**而不是假设内存里的状态是对的**；
- **未知订单**：先查状态，再决定撤单或等待，**绝不重复下单**；
- **优雅降级**：行情断了应停止开新仓，但不一定要立即平仓。

> **"重连后先对账"这一步叫 reconciliation，是实盘系统最容易出错的地方。**
> 因为它"不影响回测"，所以最常被跳过——
> **但它决定你能不能活过第一个故障日。**

### 4. 日志与审计

所有订单、回报、风控拒绝、异常都要落盘，**带毫秒级时间戳与序列号**。

> 日志是事后归因与合规审计的**唯一依据**。
> 出事之后你需要的不是"我猜当时是什么情况"，是"把那 30 分钟的回放出来"。

## 五、回测里怎么保守模拟

### 规则 1：信号与成交必须错期

**信号用第 t 日收盘价算，交易在第 t+1 日执行。** 这是最低要求。

在平台上，`BacktestConfig(t_plus_1=True)` 就是这条约束的开关。

### 规则 2：价格劣化

$$P_{\text{fill}} = P_{\text{signal}}\times(1 + s\cdot\text{side})$$

| 符号 | 白话 |
| --- | --- |
| $P_{\text{signal}}$ | 信号价 |
| $s$ | 滑点（买入向上、卖出向下） |
| side | 买卖方向 |

**日频 A 股建议的保守滑点**：

| 标的 | 保守滑点 |
| --- | --- |
| 沪深 300 成分 | 5~10 bps |
| 中证 500 成分 | 10~20 bps |
| 小市值 / 低流动性 | **30~100 bps** |

（再叠加 [09-03 冲击成本](./09-03-冲击成本模型.md)，才是完整假设。）

### 规则 3：注入延迟与故障

- **延迟**：把信号生效时间后移 k 根 K 线；
- **成交概率**：限价单**不应假设 100% 成交**；
- **故障**：随机丢弃若干交易日的订单（模拟断线）；
- **容量**：按参与率上限截断成交量。

## 六、用平台跑三档假设 + 断线模拟

按 [00-开始之前](../01-入门/00-开始之前.md) 装好环境，把下面这段存成文件跑一次：

```python
import warnings
warnings.filterwarnings("ignore")
import numpy as np
from qd.data.synthetic import generate_demo_market
from qd.backtest import Backtest, BacktestConfig
from qd.strategy.builtin import sma_cross
from qd.utils.calendar import trading_days
from qd.metrics.perf import sharpe, annual_return, max_drawdown

md = generate_demo_market(n_symbols=30, start="2018-01-01", end="2024-12-31", seed=7)

# 校准：确认回测用的交易日历与数据一致
cal = trading_days("2018-01-01", "2024-12-31", market="A")
print("交易日数 %d，数据日期数 %d" % (len(cal), len(md.dates)))

scenarios = {
    "乐观(当日成交, 5bps)":  dict(slippage_bp=5),
    "中性(次日成交, 20bps)": dict(slippage_bp=20),
    "保守(次日成交, 50bps)": dict(slippage_bp=50),
}
for name, kw in scenarios.items():
    cfg = BacktestConfig(initial_cash=1_000_000, commission_rate=0.0003,
                         stamp_duty=0.0005, **kw)
    res = Backtest(md, sma_cross(fast=10, slow=60), cfg).run()
    r = res.equity.pct_change().dropna().values
    # annual_return / max_drawdown 吃净值；sharpe 吃收益
    print("%-26s 年化=%6.2f%% 夏普=%.2f 回撤=%6.2f%%"
          % (name, annual_return(res.equity)*100, sharpe(r),
             max_drawdown(res.equity.values)*100))

# 故障模拟：随机 2% 的交易日无法交易（收益记 0）
r = res.equity.pct_change().dropna().values
rng = np.random.default_rng(7)
mask = rng.random(len(r)) < 0.02
r_gap = np.where(mask, 0.0, r)
nav_gap = np.cumprod(1 + r_gap)
print("断线 2%% 交易日后：年化 %.2f%% → %.2f%%"
      % (annual_return(res.equity)*100, annual_return(nav_gap)*100))
```

我实跑的结果：

```
交易日数 1827，数据日期数 1827

乐观(当日成交, 5bps)    年化= -0.13% 夏普=0.08  回撤=-49.60%
中性(次日成交, 20bps)   年化= -2.83% 夏普=-0.06 回撤=-56.20%
保守(次日成交, 50bps)   年化= -8.25% 夏普=-0.38 回撤=-67.08%

断线 2% 交易日后：年化 -8.25% → -9.39%
```

**三个读点：**

**第一，假设越保守，结果单调变差**：-0.13% → -2.83% → -8.25%。**这是"态度"的价格。**

**第二，回撤也跟着恶化**：-49.6% → -56.2% → -67.1%。

> **成本不只降收益，还放大回撤。**
> 因为亏损的时候你也要交易（止损、调仓），成本在亏损期**同样要付**，
> 于是"跌的时候更跌"。**这是很多成本分析的盲点。**

**第三，断线 2% 的交易日，年化从 -8.25% 恶化到 -9.39%。**

> **一个看起来"很小"的故障（2% 的日子），代价约 1.1 个百分点。**
> 如果策略年化只有 +5%，这 1.1 个百分点就是**20% 的收益损失**。
>
> **而这只模拟了"不能交易"，没模拟"错误交易"。**
> 后者才是 Knight 那种灾难。

## 七、把这一篇串起来

回到 2013 年 8 月 22 日那三个小时。

那次事故里，没有人的策略是"错的"。**所有人都在一个正常运转的系统上，直到系统不运转了。** 而量化这个行业，本质上是在**用代码和别人的系统打交道**——你能控制的只有自己这一侧。

> 06-07 讲 Knight、这一篇讲纳斯达克，两个故事合起来说的是同一件事：
> **"策略正确"只是起点。从"策略正确"到"钱到账"，中间隔着一整套工程可靠性。**

> 一句话收尾：
> **回测假设你永远在线、永远能成交、永远不重复下单。**
> **而实盘唯一确定的事，是这三件事都会出问题。**
> **你的系统不是为"正常日子"设计的，是为"出问题的那天"设计的。**

## 常见坑

- **回测用当日收盘价成交**：几乎一定含前视，是回测虚高的头号原因。
- **忽略 Level-1 快照的 3 秒间隔**：用快照做分钟级回测会显著高估成交概率。
- **没有幂等 ID**：网络重试造成重复下单、仓位翻倍，是实盘事故的经典成因。
- **风控写在策略进程里**：策略崩溃时风控一起崩溃。
- **重连后不对账**：本地状态与真实持仓不一致，接下来的所有决策都是错的。
- **只用回测最优参数上线**：参数应在净化交叉验证下选（[10-03](../10-机器学习/10-03-金融数据的交叉验证.md)），并对延迟做敏感性分析。
- **忽略交易所的时间规则**：集合竞价、收盘前不可撤单时段、隔夜委托生效时点。
